# Coding Standards

This document establishes the development conventions and formatting guidelines for all Home Assistant YAML configurations, Blueprints, Jinja2 templates, and test files in this repository.

## Language and Translation
- **English Default**: All names, descriptions, configuration labels, code comments, and log messages in Yaml and Python files **must be written in English** to support public distribution on GitHub.
- **Git Commit Messages**: Must be written in English.
- **Relative Markdown Links**: Never use absolute file system paths (e.g., `file:///C:/Users/...`) in markdown documentation. Always use relative paths (e.g., `./` or `../`) to prevent local directory structures or user names from leaking to public Git repositories.
- **Root README Maintenance**: The root `README.md` must be kept up-to-date at all times. Any architectural changes, new blueprint inputs, configuration options, or setup step adjustments must be updated directly in the root `README.md` as part of the same change set.

---

## Editor Configuration & Formatting
We adhere to the rules defined in the root [.editorconfig](.editorconfig):
- **Indentation**: Spaces only (no tabs).
- **Indent Size**: `2` spaces for both `.yaml` and `.json` files.
- **End of Line**: `lf` (Line Feed).
- **Encoding**: `utf-8`.
- **Trim Trailing Whitespace**: Enabled.
- **Insert Final Newline**: Enabled.

## Entity Naming Conventions

To ensure smooth integration and auto-discovery, all entity IDs and helpers must follow a strict naming convention:

| Entity Type | Pattern / Example | Description |
| :--- | :--- | :--- |
| **Status Helper** | `input_select.[device_name]_emhass_status` | Must contain options: `done`, `wait`, `running`, `force` (plus wallbox `force-6`, `force-10`, etc.). |
| **JSON Helper** | `input_text.[device_name]_emhass_json` | Stores the serialized state payload for the deferrable load. |
| **Optimizer Sensor** | `sensor.p_deferrable[index]` | Read-only sensor generated by EMHASS (e.g. `sensor.p_deferrable0`). |
| **Current/Power Sensor** | `sensor.[device_name]_leistung` | The physical energy monitoring sensor. |
| **Average/Stop Sensor** | `sensor.[device_name]statistik10` | The statistical sensor to determine if a machine is completed (usually a 10-minute average). |

### Example JSON Payload Structure (JSON Helper)
The `input_text` JSON helper is initialized and updated with the following structure:
```json
{
  "po": 1000,    // Nominal power in Watts (W)
  "ho": 1.5,     // Operating hours (h)
  "st": 0,       // Earliest start timestep (index)
  "et": 12,      // Latest end timestep (index)
  "se": false,   // Semi-continuous load (bool)
  "si": true,    // Single constant block (bool)
  "mp": 200,     // Minimum power in Watts (W)
  "pe": 0,       // Startup penalty score
  "us": "done",  // Status state matching the select helper
  "ss": 0        // Plan start timestamp
}
```

## Jinja2 Template Guidelines

Jinja2 templates used inside automation files should be clean, readable, and follow these rules:

1. **State Snapshotting**: 
   Always define a single read-only `snapshot` variable as a JSON-encoded dictionary at the beginning of the action sequence. This guarantees that all subsequent conditions and actions evaluate using consistent state values:
   ```yaml
   variables:
     snapshot: >
       {% set status_json = states(input_emhass_sensor | string) | from_json(default={}) %}
       {
         "current_time": now() | string,
         "status_sensor_value": states(input_status_sensor | string) | default('done') | string,
         ...
       }
   ```
2. **Type Safety & Default Values**:
   Always provide defaults to casting filters to prevent templates from failing:
   - Use `| int(default)` or `| float(default)` rather than simple casting.
   - Use `| bool(default)` for boolean properties.
3. **Built-in & Custom Filters**:
   Leverage the customized filters available in the Home Assistant environment:
   - `from_json(default)` and `to_json` for object translation.
   - `as_datetime` and `as_local` for timestamp processing.
   - `combine` to merge dictionaries.
