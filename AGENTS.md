# Project Rules & Development Standards

This document establishes the guidelines, coding conventions, architectural rules, tool priorities, and workflows for all AI agents and developers working in this repository.

---

## 1. Core Development & Coding Standards

### Language and Documentation
- **English Default**: All configuration labels, entity aliases, descriptions, code comments, and log messages in YAML, Python, and JSON files **must be written in English** for consistency and open-source compatibility.
- **Relative Markdown Links**: Always use relative markdown links (e.g., `./` or `../`), never absolute local paths (`file:///...` or `C:/...`).
- **README Maintenance**: Keep the root `README.md` and relevant subfolder READMEs in sync whenever blueprints, inputs, sensors, or automation architectures are modified or added.

### Formatting & Editor Rules
Adheres to the root [.editorconfig](.editorconfig):
- **Indentation**: 2 spaces (no tabs) for YAML and JSON.
- **Line Endings**: LF (`\n`).
- **Encoding**: UTF-8.
- **Whitespace**: Trim trailing whitespace and insert final newline.

### Jinja2 Template Guidelines
- **Type Safety & Explicit Defaults**: Always provide explicit defaults for all casting filters:
  - `| int(0)` or `| float(0.0)` rather than unparameterized casting.
  - `| bool(false)` for booleans.
  - Use `default(..., true)` when evaluating strings that could be empty or `None`.
- **State Snapshotting**: Define read-only `snapshot` variables as a JSON-encoded dictionary at the start of automation actions to guarantee consistent evaluation across conditions and actions.
- **Filters**: Leverage Home Assistant built-ins (`from_json`, `to_json`, `as_datetime`, `as_local`, `combine`).

### Entity Naming Conventions
| Entity Type | Pattern / Example | Description |
| :--- | :--- | :--- |
| **Status Helper** | `input_select.[device]_emhass_status` | Options: `done`, `wait`, `running`, `force` (plus wallbox `force-6`..`force-16`). |
| **JSON Helper** | `input_text.[device]_emhass_json` | Stores the serialized state payload for the deferrable load. |
| **Optimizer Sensor** | `sensor.p_deferrable[index]` | Read-only power sensor generated by EMHASS (e.g. `sensor.p_deferrable0`). |
| **Power Sensor** | `sensor.[device]_leistung` | Physical energy/power monitoring sensor. |
| **Average/Stop Sensor** | `sensor.[device]statistik10` | 10-minute average power sensor for completion detection. |

#### JSON Helper Payload Structure:
```json
{
  "po": 1000,    // Nominal power in Watts (W)
  "ho": 1.5,     // Operating hours (h)
  "st": 0,       // Earliest start timestep (index)
  "et": 12,      // Latest end timestep (index)
  "se": false,   // Semi-continuous load (bool)
  "si": true,    // Single constant block (bool)
  "mp": 200,     // Minimum power in Watts (W)
  "pe": 0,       // Startup penalty score
  "us": "done",  // Status state matching the select helper
  "ss": 0        // Plan start timestamp
}
```

## 2. Git Commit Rules (Focus on the "WHY")

Commit messages must clearly explain **WHY** a change was made rather than merely summarizing the code diff of WHAT was changed:
- **Focus on Motivation & Context**: Detail the problem solved, root cause, or architectural rationale.
- **Conventional Prefix**: Use conventional commit types (`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`).
- **Language**: English only.
- **Good Example**:
  `fix(wallbox): defer EV charging to cheap grid hours in winter when solar forecast cannot meet demand`
- **Bad Example**:
  `update goe_pv_surplus_enabled template in blueprint`

## 3. Tool Priority & Access Hierarchy

When interacting with Home Assistant, follow this strict tool priority:

1. **`ha_mcp` (Primary)**:
   - Always prefer `ha_mcp` over SSH for inspecting live entity states, evaluating Jinja2 templates (`ha_eval_template`), reading logs (`ha_get_logs`), querying health diagnostics (`ha_get_system_health`), and updating automations, scripts, helpers, or scenes.
2. **Blueprint Transfer (SFTP / SCP / `ha_manage_blueprints`)**:
   - Blueprint YAML files should be transferred via SFTP/SCP or `ha_manage_blueprints`. Note that standard SSH `admin` user on Home Assistant OS has restricted write permissions on `/config/blueprints/`.
3. **SSH (`ssh homeassistant`)**:
   - Pre-configured alias `ssh homeassistant` in `~/.ssh/config`.
   - Use SSH for OS-level diagnostics, container inspection, running helper scripts (e.g. `tools/run_system_health.ps1`), or reading SQLite DB when MCP does not provide direct support.
4. **Git Repository (Single Source of Truth)**:
   - Changes are developed and validated locally in the Git repository before being deployed to Home Assistant.

---

## 4. Local Docker Container-First Philosophy

To ensure zero friction when migrating between workstations or environments:
- Execute all tests, linters, simulation environments, and validation scripts inside **local Docker containers** (e.g. `.\tests\run_tests.ps1`).
- Avoid depending on local host-installed Python runtimes or host system tools where a containerized equivalent exists.
- Always verify Docker engine availability (`docker info`) before test execution.

---

## 5. Continuous Skill Maintenance

The skills located in `.agents/skills/` are persistent knowledge bases for autonomous tasks:
- **Mandatory Updates**: Whenever an architecture, blueprint input, integration entity, API, or automation logic changes, the relevant skill(s) **must be updated immediately** in the same changeset.
- **Token Efficiency**: Refine skill instructions continuously to keep agent interactions token-efficient and structured.

---

## 6. Testing & Bugfixing Workflow (TDD)

1. **Reproduce First**: Before modifying a Blueprint to fix a bug, create or update a test scenario in `tests/scenarios/` that reproduces the defect.
2. **Confirm Failure**: Run `.\tests\run_tests.ps1` to confirm the test fails.
3. **Implement Fix**: Modify the Blueprint, ensuring all existing and new tests pass inside Docker.
